# Notion Writer

Notion MCP(`mcp__Notion__*`)로 페이지를 읽고 쓰는 절차와, 실제로 겪은 함정을 정리한 스킬이다.
Notion은 표준 마크다운이 아니라 "Notion-flavored Markdown"을 쓴다. 표는 HTML 태그, 콜아웃과 토글은 XML 태그, 일부 특수문자는 반드시 이스케이프해야 한다. 이 차이를 모르고 쓰면 표가 깨지거나 물결표가 취소선으로 바뀐다.

## 작업 순서

### 1. 대상 페이지를 확정한다

- 사용자가 "같은 노션", "그 페이지", "아까 그거"라고 하면 새 페이지를 만들지 말고 기존 페이지를 찾는다.
  `mcp__Notion__notion-search`(키워드)와 `mcp__Notion__notion-list-recent-pages`(최근 열람)를 같이 호출하면 대부분 한 번에 찾는다.
- URL이나 ID를 받았으면 바로 `mcp__Notion__notion-fetch`로 연다.
- 목적지를 전혀 말하지 않았고 새 문서가 필요하면 `notion-create-pages`에 `creation_mode: "draft"`로 비공개 초안을 만들고, 결과 보고에서 비공개라는 점과 원하는 위치로 옮길 수 있다는 점을 알린다.

### 2. 쓰기 전에 현재 내용을 읽는다

`notion-fetch`로 페이지 전문을 받아 둔다. 이유는 세 가지다.

- 기존 구조(제목 레벨, 이미 있는 섹션, 톤)에 맞춰야 이어 붙인 티가 안 난다.
- 부분 수정(`update_content`)의 `old_str`은 fetch 결과와 글자 단위로 일치해야 한다. 기억이나 추측으로 쓰면 실패한다.
- 이미 같은 내용이 있는지 확인해 중복을 막는다.

### 3. 문법 규격을 확인한다

처음 쓰는 세션이면 `notion-fetch`에 `id: "notion://docs/enhanced-markdown-spec"`을 넣어 규격 전문을 읽는다. 자주 쓰는 부분은 `references/notion-markdown-cheatsheet.md`에 요약해 두었으니, 규격 전문을 다시 읽기 부담스러우면 그 파일만 봐도 된다.

### 4. 본문을 작성한다

작성 원칙은 아래 "본문 작성 규칙"을 따른다. 긴 문서는 로컬 파일에 먼저 써 두고 검토한 뒤 보내면 실수를 줄일 수 있다.

### 5. 쓰기 방식을 고른다

| 상황 | 명령 | 비고 |
|---|---|---|
| 기존 페이지 끝에 새 섹션 추가 | `notion-update-page` + `command: "insert_content"` + `position: {"type":"end"}` | 가장 안전. 기존 내용을 건드리지 않는다 |
| 기존 문장·표 일부 수정 | `notion-update-page` + `command: "update_content"` + `content_updates: [{old_str, new_str}]` | 한 호출에 여러 교체를 배열로 넣는다 |
| 페이지 전체 교체 | `notion-update-page` + `command: "replace_content"` | 하위 페이지가 삭제될 수 있어 `allow_deleting_content`가 없으면 실패한다. 꼭 필요할 때만 |
| 새 페이지 | `notion-create-pages` | `properties.title`에 제목, `content`에는 제목을 넣지 않는다 |

다음 단계에서 결과를 확인해야 하면 `allow_async: false`를 준다. 비동기로 두면 fetch 시점에 반영이 안 되어 있을 수 있다.

### 6. 결과를 확인하고 보고한다

쓴 뒤 `notion-fetch`로 다시 읽어 표·콜아웃·목차가 의도대로 들어갔는지 본다. 보고에는 페이지 링크, 무엇을 추가·수정했는지, 비공개 초안이면 그 사실을 적는다.

## 본문 작성 규칙

### 이스케이프가 필요한 문자

`\ * ~ ` $ [ ] < > { } | ^` 는 본문에서 그대로 쓰면 서식으로 해석된다. 특히 한국어 문서에서 자주 걸리는 것은 다음이다.

- 물결표 `~`: "3만~5만 원", "1~7단계"처럼 범위에 쓰면 취소선으로 바뀐다. `\~`로 이스케이프하거나 "3만에서 5만 원"으로 바꿔 쓴다.
- 세로줄 `|`: 표를 마크다운 파이프로 그리면 안 된다. `<table>` 태그를 쓴다.
- 대괄호 `[ ]`: 링크나 체크박스로 해석된다. "[참고]" 같은 표기는 "(참고)"로 바꾼다.
- 꺾쇠 `< >`: 태그로 해석된다. 비교 표현은 "미만", "초과"로 풀어 쓴다.
- 화살표 `→`, 가운뎃점 `·`, 괄호, 퍼센트, 슬래시는 안전하다.

코드 블록 안에서는 이스케이프하지 않는다.

### 블록 문법 요점

- 제목: `#`, `##`, `###`, `####`까지. 5, 6단계는 4단계로 바뀐다.
- 목록: `- `, `1. `. 하위 항목은 탭으로 들여쓴다(스페이스 아님).
- 구분선: `---`
- 목차: `<table_of_contents/>` 한 줄. 긴 분석 문서 상단에 넣으면 좋다.
- 콜아웃:
  ```
  <callout color="gray_bg">
  	본문. 여러 블록을 탭 들여쓰기로 넣을 수 있다.
  </callout>
  ```
  `icon` 속성은 선택이다. 사용자가 이모지를 싫어하면 생략한다.
- 표: `<table header-row="true" fit-page-width="true">` 안에 `<tr>`, `<td>`. 셀에는 리치 텍스트만 들어간다(목록·제목 불가). 굵게는 `**`로 쓰고 `<b>`는 쓰지 않는다.
- 토글 제목: `## 제목 {toggle="true"}` 다음 줄부터 자식 블록을 탭 들여쓰기. 들여쓰지 않으면 토글 밖으로 나간다.
- 페이지 언급: `<mention-page url="...">제목</mention-page>`. 절대 `<page url="...">`를 쓰지 않는다. `<page>`는 그 페이지를 현재 페이지 아래로 옮겨 버린다.
- 빈 줄은 무시되므로 간격을 띄우려고 빈 줄을 넣지 않는다. 꼭 필요하면 `<empty-block/>`.
- 인용 여러 줄은 `> 첫 줄<br>둘째 줄`처럼 한 블록 안에서 `<br>`로 잇는다.

### 전체 교체(`replace_content`)의 함정

- 교체 직전에 반드시 `notion-fetch`를 다시 한다. 마지막으로 읽은 뒤 사용자나 다른 세션이 하위 페이지를 만들었을 수 있다. 하위 페이지가 `new_str`에 없으면 API가 "would delete N child page(s)" 오류로 거부한다.
- 오류가 나면 `allow_deleting_content: true`로 밀어붙이지 않는다. 그 하위 페이지를 fetch로 읽어 내용을 파악한 뒤, `new_str`끝에 `<page url="...">제목</page>` 태그를 넣어 보존한다. 관련 문서라면 상단 콜아웃에서 `<mention-page>`로 교차 참조까지 해 준다.
- fetch 결과에서 `<page url="...">` 태그는 본문 마지막에 나타난다. 그 위치를 유지하려면 `new_str`의 마지막 줄에 그대로 둔다.

### 부분 수정(`update_content`)의 함정

- fetch 결과에서 표는 `<tr>\n<td>` 처럼 탭 들여쓰기 없이 돌아온다. `old_str`은 그 형태 그대로 복사한다.
- 같은 문자열이 두 군데 이상 있으면 실패한다. 표 마지막 행처럼 반복되는 조각은 뒤에 오는 제목이나 앞 셀 내용까지 포함해 유일하게 만든다.
- 표 중간에 행을 넣을 때는 바로 앞 행 전체를 `old_str`로 잡고 `new_str`에 그 행과 새 행을 함께 넣는다.
- 여러 군데를 고칠 때는 `content_updates` 배열 하나로 보낸다. 호출을 나누면 중간 상태에서 fetch 결과가 달라져 다음 `old_str`이 어긋날 수 있다.

## 문서 구성 관례

이 저장소의 사용자는 정리 문서에서 다음을 선호한다. 특별한 요청이 없으면 이 틀을 기본으로 한다.

- 이모지를 쓰지 않는다. 콜아웃 아이콘도 생략한다.
- 흐름은 배경 → 분석 → 결론(추천) → 다음 단계 순서.
- 분석 문서 상단에 콜아웃으로 작성일, 근거 자료, 분석 틀, 전제를 한 번에 적는다.
- 여러 항목을 비교할 때는 종합 비교표를 먼저 두고 항목별 상세 섹션을 뒤에 둔다. 각 상세 섹션은 기본 정보 표 / 개요 / 강점 / 리스크와 약점 / 검증해야 할 핵심 가설 / 개선 제안 / 평가 순서. 정확한 틀은 `references/idea-analysis-template.md`를 따른다.
- **모든 항목을 같은 양식으로 쓴다.** 어떤 항목의 원문이 이미 페이지에 있거나 다른 페이지에 있어도, "위 참조" 또는 링크만으로 대체하지 않는다. 그 항목도 다른 항목과 똑같은 소제목과 순서로 다시 정리한다. 원문 메모는 삭제하지 말고 해당 항목 안의 토글(`<details>`)에 보존한다. 사용자는 양식이 다른 항목이 하나라도 섞여 있으면 재작업을 요청했다.
- 항목 하나를 새로 추가할 때는 종합 비교표와 세부 점수표에도 같은 항목의 행을 넣고, 공통 인사이트에서 언급하는 건수(예: "양면 플랫폼이 7건")를 함께 갱신한다.
- 문서에 없는 사실을 보탤 때는 "추정"이라고 표시한다. 규제·법률 관련 내용은 전문가 확인이 필요하다고 명시한다.
- 숫자는 표 안에 두고 본문 문장에는 최소로 넣는다.
- 기존 페이지에 이어 붙일 때는 `---` 구분선 뒤에 `#` 제목으로 새 섹션을 시작하고, 기존 내용은 손대지 않는다.

## 예시: 기존 페이지에 분석 섹션 추가

```
---
# 사업화 아이디어 분석 (3건)
<callout color="gray_bg">
	**분석 기준일**: 2026-09-04. 제출 문서 3건을 동일한 틀로 분석했다.
	**분석 틀**: 문제 절실함 / 시장 크기 / 실행 가능성 각 5점.
</callout>
<table_of_contents/>
## 종합 비교
<table header-row="true" fit-page-width="true">
	<tr>
		<td>아이디어</td>
		<td>핵심 리스크</td>
		<td>합계</td>
	</tr>
	<tr>
		<td>A</td>
		<td>콜드스타트</td>
		<td>12</td>
	</tr>
</table>
## 1. A
### 개요
- 문제: ...
### 개선 제안
- 범위를 한 지역으로 좁힌다.
```

이 내용을 `notion-update-page`에 `command: "insert_content"`, `position: {"type":"end"}`, `allow_async: false`로 보낸 뒤 `notion-fetch`로 확인한다.

## 자료가 PDF나 이미지일 때

정리할 원본이 PDF이면 먼저 텍스트를 뽑는다. `pdftotext`가 없으면 `pip install pymupdf` 후 `page.get_text()`로 추출하고, 텍스트가 비어 있는 스캔본은 `page.get_pixmap(dpi=110).save(...)`로 PNG를 만들어 Read 도구로 읽는다. 추출한 내용은 Notion에 그대로 붙이지 말고 요약·구조화한 뒤 쓴다.
